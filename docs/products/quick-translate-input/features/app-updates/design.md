# アプリの自動更新の設計

## このドキュメントについて

[Requirements](requirements.md)と[Product](../../product.md)に基づき、署名を固定した配布とSparkleによる更新を設計する。

### 対象読者

配布と更新処理を実装・保守する開発者とエージェント。

### 前提知識

macOSはアプリの署名に含まれる識別条件で、更新前後のアプリを同一と判断する。
仮署名ではこの条件が個々のビルドに結び付くため、更新をまたいだ権限の維持には向かない。
[Appleの説明](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)を参照する。

### このドキュメントで扱わないこと

翻訳処理、Appleの公証、Developer IDでの配布は扱わない。

## 実装方針

アプリの置き換えはSparkle 2.10.0に任せる。
起動時に配布用の設定を持つバンドルだけ更新処理を開始し、メニューバーとアプリメニューに更新確認と自動更新の設定を置く。
初期値はInfo.plistで指定し、利用者の選択はSparkleの設定APIで変更する。
自動ダウンロードした更新は通常の終了時に適用し、手動確認ではSparkleの標準画面を表示する。
動作は[Sparkleの設定](https://sparkle-project.org/documentation/customization/)に従う。

### 配布版の識別と署名

アプリの署名には、長期に保管する自己署名のコード署名証明書を使う。
配布用の公開設定として証明書のSHA-256とSparkleの公開鍵を保存する。
署名の識別条件をアプリ識別子と固定証明書のハッシュに結び付け、内容の異なる次版も同じ条件を満たすようにする。
配布時は固定証明書の一致と署名の有効性を確認し、仮署名への自動切り替えはしない。
自己署名の性質は[AppleのCode Signing Guide](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/AboutCS/AboutCS.html)を参照する。

Sparkleのフレームワークはシンボリックリンクと実行権限を保って同梱する。
外側のアプリを署名する前に、同梱する実行ファイル、補助アプリ、フレームワークを内側から署名する。
開発用ビルドでも同梱するが、更新設定を入れず、配布版への自動移行を防ぐ。

## アーキテクチャ・シーケンス図

単一の更新コントローラーがSparkleへ処理を委ねるため、図は省略する。
起動、署名付き配信情報の取得、アーカイブの検証、ダウンロード、終了時の適用の順に進む。

## データモデル・ER 図

公開設定には証明書のSHA-256とSparkleの公開鍵を持たせる。
Info.plistには配布版の識別、配信情報のURL、公開鍵、自動更新の初期値を入れる。
更新の選択と確認時刻はSparkleがUserDefaultsへ保存する。
リレーショナルデータを扱わないためER図は省略する。

## API・インターフェース

### 利用者の操作

メニューの「Check for Updates…」で手動確認を開始する。
「Automatically Check for Updates」と「Automatically Install Updates」で設定を変更する。
確認中は重複する確認操作を無効にし、自動確認が無効なら自動適用の設定も操作不可にする。

### アプリ内部

SPUStandardUpdaterControllerをアプリの寿命にわたって保持する。
未設定の開発用ビルドでは生成せず、テストの起動でもネットワークに接続しない。
バックグラウンドアプリの更新表示は標準ドライバーに任せ、他アプリの入力フォーカスを奪わない。

## 外部サービスとの連携方式

GitHub Releasesの最新リリースのアセットとしてappcast.xmlを配信する。
各版のZIPはその版のタグのURLを使い、最新リリースの変更後も参照を固定する。
フィードとアーカイブの生成・署名には、依存として解決した同じSparkleのツールを使う。
HTTP通信や更新アーカイブの展開・置換は独自に実装しない。

## データの取り扱い設計

更新設定は同じバンドル識別子のユーザー設定に保存し、翻訳の設定は変更しない。
署名付きの配信情報とアーカイブはSparkleの保存・削除処理に従う。
翻訳対象の文章、クリップボード、キー入力履歴は更新処理へ渡さない。

## 認証認可に関する特記事項

公開アセットの取得にログイン情報は使わない。
CIでは一時キーチェーンへコード署名鍵を読み込み、配布後に破棄する。
CIの一時ランナーでは証明書をコード署名用途に限って信頼し、終了処理でその設定を削除する。
開発者のMacでは専用コマンドで一度だけユーザーのコード署名用の信頼設定へ登録し、通常のビルドから信頼設定を書き換えない。
コード署名のPKCS#12、そのパスワード、Sparkleの秘密鍵はGitHub Actions Secretsで渡す。
公開設定の証明書と実際の署名証明書が一致しない場合は、アーカイブの公開前に失敗させる。

## セキュリティ上の留意事項

HTTPS、アーカイブの展開前の署名検証、フィードの署名検証を有効にする。
配信統計の送信は無効にする。
署名後のフィードを書き換えず、同じ署名鍵を長期保管する。
Developer IDによる鍵の切り替えを使えないため、鍵を失った場合は自動更新を継続できない。新しい鍵での手動再インストールが必要になる。

## デプロイに関する特記事項

最初の公開前に固定署名の公開設定を作り、3つのSecretsを設定する。
公開設定や秘密鍵が欠ける場合はリリースを停止する。
最初の固定署名版は手動で入れ、アクセシビリティ権限を再登録する。
その後は同じパス、バンドル識別子、署名証明書を使う。
既存の公開済みリリースは変更しない。

## 検討した代替手段

### Developer IDと公証

初回の警告を減らし、一般向け配布に向くが、有料登録が必要なので今回は採用しない。

### 仮署名のまま自動更新

配布作業は簡単だが、更新後の権限維持という目的を満たさない。

### 独自のダウンロードと置き換え

補助プロセス、署名検証、終了や失敗時の復旧まで独自に実装する必要があるため、Sparkleを選ぶ。

## 未決事項

なし。公開設定とSecretsの生成・登録は初回公開の準備作業として扱う。
